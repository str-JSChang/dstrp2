Different structures answer different questions.

Task 1 · Where is my parcel?

The record list owns the full data. Head insertion displays the newest parcel first. Intake keeps only IDs and processes the oldest arrival first.

Task 2 · Which request goes next?

Sorted linked insertion places Urgent before Normal. Equal-priority requests keep creation order. Click to reveal the insertion trace.

Order: Normal A, Urgent B, Normal C, Urgent D becomes B → D → A → C. The first Pending request is recommended; staff can choose another ID.

Task 3 · Who handles it?

C1 and C2 are counters. D1 is delivery personnel. Allocate then release one request at a time below to see separate round-robin cursors. The real application skips Occupied and Unavailable resources.

A circular list links the last node back to the first. Counters and delivery personnel each remember their own next position.

List lookup O(P)
Walk through parcel nodes until the ID matches. P means stored parcels.

Priority insertion O(R)
Find the sorted position. Retained terminal requests count toward R.

Resource selection O(S)
Scan at most one circular cycle. S means resources.

Queue enqueue, dequeue and peek are O(1). Whole registration is O(P) because it checks duplicates. Linked structures grow dynamically; arbitrary searching still takes traversal.

Quick oral questions — reveal suggested answers

Why both structures? The record must remain searchable after intake ends. The queue only represents waiting order.

Why store IDs? One parcel record remains the source of truth instead of several changing copies.

Why validate before releasing? A wrong recipient or invalid completion must not free an occupied resource while work is still active.

Why a destructor? Every manually allocated node must be freed. Owning structures disable copying to prevent shallow copies and double deletion.

Why separate cursors? Alternating delivery and counter allocations should not reset the other resource type’s rotation.

README.md

Smart Campus Parcel System

Integrated C++17 console prototype for Tasks 1, 2 and 3 of the three-member assignment. It uses manually implemented linked structures and coordinated status updates. Data lives in memory until the program exits.

Build, test and run

On Linux, open a terminal in the project folder containing src and include. With g++ installed, compile and run:

mkdir -p build
g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror -I include src/main.cpp src/task1.cpp src/task2.cpp src/task3.cpp -o build/parcel_system
./build/parcel_system

The -I include option lets the compiler find the project's headers. Run the compile command again after changing the C++ code.

In PowerShell, from this folder:

./build.ps1 -Test
./build/parcel_system.exe

Requirements: GCC supporting C++17 on PATH; Python 3 for the console tests. The script builds with -Wall -Wextra -Wpedantic -Werror and stops on failed builds or tests. To build only the application, run ./build.ps1.

Alternative CMake configuration (CMake 3.16+, a C++ compiler):

cmake -S . -B build-cmake
cmake --build build-cmake
Push-Location build-cmake
ctest --output-on-failure
Pop-Location

For Visual Studio generators use cmake --build build-cmake --config Debug and ctest -C Debug --output-on-failure from the build directory. The application then resides in build-cmake/Debug/parcel_system.exe. Python console tests register in CTest when Python is found. C++ tests register when BUILD_TESTING is enabled. The GCC/PowerShell route was tested here; CMake was not installed on this machine.

Quick demonstration

  1. Register a parcel in Task 1; its generated ID starts at P1.
  2. Process the next parcel for collection with normal priority; R1 is created.
  3. Register counter C1 in Task 3, then assign R1 to a counter.
  4. Process R1 in Task 2, then complete with outcome details and its recipient ID.
  5. Search P1 and display resources: P1 is Collected and C1 is Available.

For active requests with missing/held parcels use Task 2 option 9. It closes the current request, releases its resource and marks the parcel Missing/OnHold. Recover a missing parcel to OnHold in Task 1 before resuming a service. Delivered parcels cannot reopen for redelivery; redelivery applies only to unfinished parcels.

Verification and limits

  • 543 C++ checks across eight suites, including 100 object-lifetime cycles.
  • 28 subprocess console scenarios, including a complete collection workflow.
  • GCC warnings treated as errors, with additional -fanalyzer review.
  • Regressions cover direct request synchronization, unchanged state on rejected completion, return-to-sender status and rejecting redelivery of delivered parcels.

Tests establish covered behavior, not a guarantee of zero defects. No runtime address/leak sanitizer was run. There is no persistence, staff authentication, network service or optional Tasks 4 and 5. Recipient-ID matching is a prototype collection check, not secure identity verification.

6. Pointer traces and complexity to explain at the code

Enqueue P2 after P1

Start with front == rear, both pointing to P1. Allocate a P2 queue node with next nullptr. Set rear->next to the new node, then rear to the new node. Front stays P1. Both pointer updates are constant-time, independent of queue length.

Dequeue the only node

Copy the ID out while its node is alive. Save old = front. Move front to front->next, which is nullptr. Set rear to nullptr, then delete old. The output ID is a string copy, not a reference into deleted storage.

Delete a middle record

For head -> P3 -> P2 -> P1 -> nullptr, removing P2 finds previous=P3/current=P2. Set previous->next to current->next, making P3 point to P1, then delete P2. Head remains P3. Do not delete current before reading its next pointer.

Why successful routing calls remove rather than blindly dequeue

Service requests can also be created directly from Task 2 for a chosen parcel. That parcel might be in the middle of intake. Removing its exact ID keeps waiting membership correct for either entry point. Normal FIFO processNext chooses the front, so finding/removing that selected ID is immediate.

Let P be saved parcels, Q waiting IDs and R retained service requests. Treat field lengths as bounded for these node-count bounds; string work adds character costs.

7. Logical questions and suggested answers

Use these to practice; explain in your own words and point to the relevant code.

1. Which structures did you choose? A singly linked list for authoritative parcel records and a linked FIFO queue for temporary intake order. Both are implemented manually.

2. Why not only a queue? Processing removes waiting membership, but staff still need the record for search, status updates and service completion.

3. Why not store full Parcel copies in both? Separate copies could disagree after an edit/status update. The queue's ID refers back to the authoritative record.

4. Why does P2 display before P1? Record insertion is at head. FIFO order comes from the separate intake queue, not the record-display order.

5. Is routing itself automatic sorting by urgency? No. FIFO chooses the next intake parcel; staff classify its route. Task 2 uses urgency to order created requests.

6. Can an urgent parcel skip ahead in intake? Not through normal processNext: that operation is FIFO. Urgency applies after routing. Direct Task 2 service creation is a separate staff-selected path and removes that parcel's waiting ID.

7. Why both front and rear? Front supports O(1) next selection/removal; rear lets enqueue append without traversing the whole queue.

8. What happens if rear is not reset after the last removal? It could reference freed storage; a later enqueue might write through that invalid pointer.

9. Why use peek before changing the queue? It identifies the candidate without losing it. The service insertion must succeed before successful routing removes membership.

10. Does FIFO prohibit administrative cancellation from the middle? Normal service selection stays FIFO. Cancellation/hold/direct-service actions explicitly withdraw an ID that is no longer eligible for normal intake; they do not reorder other waiting IDs.

11. How do you prevent duplicate Parcel IDs? Generated monotonically increasing IDs avoid normal collisions; the record structure also checks ID uniqueness on insertion.

12. Are IDs globally unique forever? No. Counters restart on a fresh run because there is no persistence. Uniqueness is within this running prototype's stored records.

13. Why check tracking as well as Parcel ID? Automatically assigning a fresh ID alone would let the same physical tracking registration be entered repeatedly.

14. Why does the duplicate edit check accept its own tracking? exceptId excludes the parcel being edited, while still detecting another record with that tracking.

15. Does a nonblank recipient ID prove it is a real student? No. Intake only checks required information. Later requests match the stored ID; there is no university lookup.

16. What happens if search fails? Return nullptr and print a useful message. The caller checks the pointer before accessing fields.

17. What is the difference between const and non-const find? Both search the same list. The public-facing const result permits inspection; internal mutable lookup supports updates.

18. Why return a pointer instead of a Parcel copy? It avoids copying the whole record and identifies existing storage. It is borrowed and becomes invalid after node deletion.

19. Why reject active-request edits? Changing recipient/destination/handling information could invalidate already-created service work. The lifecycle must resolve that first.

20. Can cancelled/collected parcels reopen? No. They are terminal. Hold/missing recovery is a controlled nonterminal path; cancellation is not a general undo feature.

21. What is the difference between OnHold and Missing? OnHold is retained for staff investigation/review and can resume. Missing requires explicit recovery to OnHold first.

22. Why cannot Task 1 directly change an active parcel to Missing? It might leave a live request/resource processing a missing parcel. Task 2 interruption closes/detaches that work and updates the parcel coherently.

23. What if a required service cannot be created? createRequest returns false before committing status/queue changes. The valid waiting parcel is not silently lost.

24. Why friend class ServiceModule? It grants that cooperating module controlled access for synchronized status and intake changes. Ordinary menu code cannot mutate private storage.

25. Does declaring a friend remove all design risks? No. It couples the modules; the cooperating implementation must still preserve the invariants and be tested.

26. Why keep try/catch during registration? Record insertion happens before queue allocation. If the second allocation throws, rollback removes the partial registration.

27. Why initialize node data with new Node{parcel}? If copying a string fails during initialization, C++ releases that allocation automatically. Pointer linkage is performed separately after construction succeeds.

28. What does swap do in updateParcel? After validation and preserving saved identity/time/status, it exchanges the prepared replacement with the stored record. The old details leave with the local replacement instead of partially overwriting fields.

29. Why disable copying of your structures? A shallow copy would share node pointers; both destructors could delete the same nodes. No deep-copy feature is needed here.

30. Can you claim all operations are O(1)? No. Only specific queue operations are O(1). Record validation/search and integration perform traversals.

31. What improvement did review produce? Direct tracking traversal replaced repeated ID searches. We also ensure service creation synchronizes parcel status and waiting membership, and failed completion does not release resources prematurely.

32. What is your main limitation? In-memory storage and O(P) ID lookup. The prototype also assumes authorized staff and does not verify real-world recipient identities.

33. What small modification might you be asked to make? Add a field, change the allowed edit rule, print the queue length or adjust duplicate policy. Explain every place it affects: model, input, validation, display, tests and integration as applicable.

34. How would you add a waiting count? Maintain a counter consistently on enqueue, dequeue and arbitrary removal, or traverse to count in O(Q). The maintained version needs extra invariant checks; the current code does not already implement it.

35. What if a cancelled parcel is removed but a terminal request remains? The request retains the former Parcel ID as inactive historical text. It cannot be processed; staff can explicitly remove that terminal request too.

2. C++ concepts used throughout

  • using namespace std; permits string, cout and getline without std::, as requested. Header-wide imports follow the reference, although larger libraries commonly avoid them to reduce name clashes. namespace campus groups our own types.
  • Include guards prevent repeated type definitions within one translation unit.
  • A struct groups fields; a class combines operations and private storage. enum class gives statuses and types named values, avoiding accidental mixing.
  • Node* stores a node address. nullptr means no node. -> accesses a field through its pointer. &current->value returns a pointer to a stored record.
  • const Parcel* allows inspection without modification. Returned pointers are borrowed, so do not retain them after the corresponding node is deleted.
  • const string& avoids copying an input. A by-value Parcel parcel is intentionally copied so normalization cannot mutate the caller's original object.
  • Constructors initialize objects; destructors free every owned node. Owning classes delete their copy constructor/assignment to prevent shallow copying and double deletion.
  • A reference member such as ParcelModule& parcels refers to one existing module. In parcels(parcels), the left name is the member and the right name is the parameter.
  • friend class allows a cooperating module to perform coordinated lifecycle changes. It is deliberate coupling, not a security boundary or method-level access control. Assignment hooks are private, preventing ordinary console code from forging links.
  • new creates a node; delete frees it. Save the next address before deletion. Reading head->next after deleting head would be a use-after-free error.
  • swap exchanges already-prepared values. Completion prepares outcome text before mutation, then swaps it into the request without allocating another string.

3. Shared records, policies and invariants

A Parcel stores its ID, recipient name/ID/contact, carrier, tracking number, destination, type, arrival time and status. A ServiceRequest stores its own ID, Parcel ID, service, priority, creation sequence/time, recipient, assignment and outcome. A Resource stores ID, name, type, status and assigned Request ID. Empty assignment strings mean no active assignment. Cross-module references use IDs, not record copies.

Parcel/request IDs are generated as P1/P2 and R1/R2. They restart each process because there is no persistence. Resource IDs are entered by staff and checked for uniqueness. Caller-supplied parcel/request IDs are replaced during registration. Stored tracking numbers must be unique. Comparisons are case-sensitive. trim removes outside spaces, tabs and line endings; it does not remove spaces inside names. Recipient and contact validation requires nonblank fields; the brief does not specify institutional ID or telephone formats, so the prototype does not claim to validate those formats.

Invariants

  1. The parcel list owns parcel data; intake holds only waiting IDs.
  2. Each parcel has at most one active service request.
  3. Active requests have matching parcel recipient IDs and expected service statuses.
  4. Assigned/InProgress requests reference Occupied resources of the correct type. The resource points back to the same Request ID. Pending requests are unassigned.
  5. Completed/Cancelled/Returned requests are inactive and unassigned.
  6. Collected/Delivered/Returned/Cancelled parcels are terminal and cannot reopen.
  7. Rejected normal business operations preserve the existing parcel, request and assignment. A failed allocation cannot occupy a resource.

This is a single-threaded application-level consistency design. It is not a database transaction, distributed lock or concurrent scheduler.

Service policy

Service Active parcel status Resource Completed outcome
Collection AwaitingCollection Counter Collected / request Completed
CampusDelivery AwaitingDelivery Delivery personnel Delivered / request Completed
Redelivery AwaitingDelivery Delivery personnel Delivered / request Completed
SpecialHandling SpecialHandling Delivery personnel OnHold / request Completed
ReturnToSender ReturnPending Delivery personnel Returned / request Returned

An explicit Returned outcome ends a valid in-progress service as Returned. ReturnToSender always produces Returned, even when the menu outcome is Completed. SpecialHandling leaves OnHold for the next staff decision. These are documented team rules, not policies dictated by the assignment.

Redelivery is another attempt on an unfinished parcel. Interrupt a delivery to OnHold, then create Redelivery. A Delivered parcel cannot reopen. Recover a Missing parcel to OnHold before creating or resuming a service.

4. Task 1 - intake, sorting and processing

Requirements and code

Requirement Implementation
Register registerParcel validates/normalizes details, rejects duplicate tracking, generates ID/time and enqueues the ID.
Maintain/locate ParcelRecords owns records; lookup/display functions expose relevant details and status.
Sort/process processNext selects FIFO intake and maps a route to Task 2; investigation instead holds the parcel.
Update/remove Edits preserve identity/time/status; active/terminal edits fail; deletion requires Cancelled and no active request.
Exceptions Empty intake, duplicates, invalid recipient details/routes, unknown IDs and completed parcels are handled.

Why a list and a queue?

The singly linked list retains current parcel records. Each node contains a Parcel and next pointer. The FIFO queue contains only waiting Parcel IDs and has front/rear pointers. Leaving intake must not destroy the parcel: requests still need its details.

Record insertion is at the head, so record display is newest-inserted first. Intake processing is separately FIFO. ID lookup follows next until matching or nullptr. Duplicate tracking is checked by one direct traversal, replacing the ZIP's repeated generated-ID searches, which could take quadratic time.

Registration algorithm

  1. Trim required fields and reject incomplete data.
  2. Traverse records once to reject duplicate tracking.
  3. Prepare the next P-number, local timestamp and Received status.
  4. Insert the parcel node, then enqueue its ID.
  5. If queue allocation throws, remove the inserted record and rethrow.
  6. Increment the ID counter after both insertions succeed.

Unexpected runtime exceptions reach main and stop the process with an error message. This prototype does not attempt recovery after memory exhaustion or counter exhaustion.

Queue and deletion pointer cases

Enqueue allocates a node with next == nullptr. Empty queue: front and rear both point to the new node. Nonempty queue: connect the old rear, then advance rear. Dequeue copies the front ID, advances front and deletes the old node. Removing the final node must reset rear to nullptr. remove(id) also handles arbitrary head/middle/tail/only removal; removing the tail changes rear to previous.

Record deletion keeps previous/current pointers. At the head, replace head with current->next. Otherwise bypass current through previous->next. Delete only after rewiring. Missing IDs return false without changing links.

Routing and editing

processNext validates route/priority, skips stale non-Received waiting entries and handles the earliest valid parcel. Task 2 creates a service request, then changes parcel status and removes the waiting ID after insertion succeeds. Investigation marks OnHold and removes the waiting entry without creating a request. Resume requires OnHold; Missing must first be explicitly recovered to OnHold.

Edits are blocked during active work because recipient/destination/handling changes could invalidate the linked request. The replacement retains saved ID, arrival time and status before swapping into place. Staff status updates only allow Missing, OnHold or Cancelled without active work. Active exceptions use Task 2 interruption.

Complexity

P = parcel records, Q = waiting IDs, R = retained requests. String lengths are treated as bounded; copying/comparing variable strings adds their character costs. Space is O(P+Q).

Operation Time
Record search / duplicate tracking / removal O(P)
Record insert with duplicate-ID check O(P); pointer linking alone is O(1)
FIFO enqueue/dequeue/peek O(1)
Arbitrary waiting-ID removal O(Q)
Registration O(P)
Edit details O(P+R)
Remove cancelled parcel O(P+R+Q)
Normal FIFO service routing O(P+R); removal is O(1) when the waiting ID is front
Routing with many stale IDs O(Q*P+R) conservative worst case

A linked list avoids fixed capacity but does not give constant-time arbitrary lookup. An extra index could improve lookup at the cost of more structures and synchronization.

Priority insertion

Urgent precedes Normal in the enum, so its value compares smaller. Sequence increases for successful creation. Traverse while existing nodes have earlier priority or the same priority and an earlier/equal sequence. Insert before the first later node. Equal sequences remain stable at the structure level; the module generates unique ones.

Terminal requests remain until explicit removal so staff can inspect them and repeated processing can be rejected. Therefore nextPending is O(R), not necessarily O(1). It may skip assigned and terminal nodes. The first Pending request is recommended; staff can explicitly choose another ID to avoid blocking all other work behind a resource type that is unavailable. Priority is a recommendation, not a hard scheduler.

Request states

Pending -> Assigned -> InProgress -> Completed/Returned

Any active stage can be cancelled. Manual resource release or an unavailable resource returns its request to Pending with the same original sequence/priority. Interruption for Missing/OnHold closes only the current request as Cancelled, with an explanatory outcome, and marks the parcel Missing/OnHold. It preserves a recovery route. Full cancellation instead makes the parcel terminal Cancelled.

Four ZIP regressions corrected

Direct request leaves parcel Received Successful creation sets serviceStatus(type) and removes waiting membership.

Completion algorithm

  1. Find request; require InProgress and Completed/Returned outcome.
  2. Prepare trimmed outcome text; require entered recipient ID to match.
  3. Check parcel existence, expected service status and matching recipient.
  4. Check resource existence, Occupied state, compatibility and reverse Request ID.
  5. Determine final statuses before any change.
  6. Release the validated resource and clear both assignment references.
  7. Set final statuses and swap in the prepared outcome string.

Wrong identity, blank outcome, invalid state or inconsistent assignment fails before release. No allocation is required after release begins. Private resource/service hooks limit assignment changes to cooperating modules. No const_cast is used.

Cancellation and interruption use the same validation-before-mutation pattern. Terminal removal rejects active/assigned records. This retained request list is not the optional Task 4 audit history; explicitly deleted requests are no longer searchable.

Circular representation

tail->next is the first node. Empty means tail == nullptr; a one-node ring points to itself. Lookup/display visit at least one node with do/while, stopping when they return to the start. A valid nonempty ring has no nullptr end marker.

Empty insertion self-links the new node and initializes both allocation cursors. Nonempty insertion connects the new node between tail and first, then advances tail. Duplicate checking makes complete insertion O(S), although splicing alone is O(1).

Per-type round robin

The two-element built-in pointer array is selection bookkeeping, not resource storage. Resources stay in the circular linked list. Index 0 tracks counters, index 1 delivery personnel. From that type's cursor, inspect at most one full cycle. Skip wrong type, Occupied and Unavailable nodes. On success save the successor as the next starting position and return the resource. Failure leaves that cursor unchanged.

In a ring C1 -> C2 -> D1 -> C1, one shared cursor can repeatedly select C1 if each counter request is followed by a D1 allocation. Separate cursors preserve progress toward C2 despite intervening delivery selections. The tests include this case. Fairness applies to eligible Available resources of the selected type, not to waiting time across urgent/normal requests or arbitrary staff overrides.

Assignment, release and cleanup

Assignment checks Pending/unassigned status, matching parcel state and resource type. It prepares the Request ID string, selects a resource, uses the private attachment hook, swaps the prepared Request ID into the resource and sets Occupied. Failure from wrong type/no capacity changes no assignment. Staff cannot directly mark an unassigned resource Occupied.

canReleaseRequest checks both directions of the link. Pending unassigned requests need no physical release, enabling cancellation before allocation. releaseForRequest detaches Assigned/InProgress work and resets the resource to Available. Completion then immediately sets the request terminal. Manual release leaves Pending instead. An occupied resource becoming Unavailable first releases safely, then changes status.

Destruction breaks tail->next to nullptr, turning the ring into a linear chain, then deletes each node once. Empty, single-node and multi-node rings are all supported.

The ring is appropriate for repeated allocation but cannot promise O(1) selection or fairness between service requests of different priorities.

9. Likely questions

Why not std containers? The brief requires manual structures; nodes and links are implemented explicitly. Strings/streams are library utilities, not substitute containers.

Why two Task 1 structures? Waiting membership ends before the parcel record's usefulness ends. A queue alone would discard searchable data too early.

What if priorities tie? Sequence preserves creation order; timestamps are displayed but are not used for tie-breaking because two requests can share the same second.

Can normal work starve? Yes, continual urgent arrivals can precede it. There is no aging mechanism. Staff may explicitly select another request when necessary.

Why O(R) insertion and nextPending? Insertion searches for position; Pending lookup may skip retained assigned/terminal nodes. No hidden heap or index is used.

What if all resources are busy? A full bounded cycle returns nullptr, leaving the request Pending and all assignments unchanged.

Why two cursors? Driver allocations must not reset counter rotation, and vice versa.

Main technical challenge? Keeping parcel/request/resource state consistent. The ZIP released too early; the fix validates the whole operation before mutation.

Why explicit missing recovery? Staff confirm recovery by moving Missing to OnHold; the system must not silently start delivery of a parcel still reported missing.

How is deletion safe? Save the successor first; ring destruction breaks the cycle; owning structures cannot be shallow-copied.

Does testing guarantee an A+ or zero mistakes? No. Tests establish covered behavior. Marks depend on the rubric and each member's ability to trace, justify and modify code.

10. Reading the expanded syntax

The readability revision keeps the same data structures, lifecycle rules and asymptotic complexity. It uses braces for branches, explicit types instead of auto, and separate checks with specific messages. Display labels and menu enum values are selected through ordinary if/else blocks rather than conditional expressions.

The shared readPriority helper reads a choice, returns false on Cancel/EOF, and writes the selected RequestPriority through its reference argument on success. Its callers check that result before using the priority. Investigation holds do not ask for a priority because they do not create service requests.

A lookup now declares its result first, then checks it separately:

const Parcel* parcel = parcels.findParcel(id);
if (parcel != nullptr) {
    printParcel(*parcel);
}

Node allocation intentionally retains initialization of the stored data:

Node* node = new Node{parcel};
node->next = head;
head = node;

The braces after Node initialize the node's Parcel value during allocation. If copying a parcel string throws, C++ releases that new allocation automatically. The next pointer starts with its in-class nullptr default; the following line explicitly connects it to the old head. Allocating an empty node and assigning its record afterwards would need an extra exception handler to avoid a leak. The initializer is a small piece of syntax worth understanding rather than removing.

Destructors, const references, scoped enums, deleted copying and private integration hooks remain because they protect ownership and consistency. The longer formatting makes execution order visible; it does not remove validation or change FIFO, priority ordering, per-type round robin or the validate-before-release rule.
